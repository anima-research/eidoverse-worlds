# Portable identity: the protocol shape, evaluated against the format freeze

> **Research and future design, not implemented protocol law.** Nothing here binds a reader or writer. The decided contract lives in [`docs/DESIGN-log-vocabulary.md`](../DESIGN-log-vocabulary.md) (§P, §F) and [`spec/PROTOCOL.md`](../../spec/PROTOCOL.md). Where this note and those differ, they win.

2026-11-04 · read-only against `~/eido/wt-vocab` (design doc `docs/DESIGN-log-vocabulary.md`, `spec/PROTOCOL.md` §1, §3.1, §6, §6a, §7a, §12, §13, §14; `shared/protocol/fold.js`, `spec/conformance/chain.py`, `spec/conformance/gov.py`, `server/directory.ts`, `server/custody.ts`, `server/aid1.ts`, `tools/protocol/import-v1/world.ts`, `tools/protocol/migrate-identities.ts`). Every codebase claim below names its line; external claims name their source at the bottom. Guesses are marked **guess**.

**One line:** make an identity a did:plc-shaped *self-certifying id* (the hash of a signed identity-genesis, with ordered rotation keys and a recovery window, resolved through a home node the person chooses), keep `actor` as the opaque `u-` id it is today, and bind the two outside the log by signed claim — so the freeze touches only the id grammar, the genesis `owners` grammar, and one sentence forbidding identity from ever entering the envelope.

## For the freeze (decide or reserve NOW; everything else is additive later)

The test for "now": would it change bytes in the chain skeleton, the genesis, or the kernel's envelope/grammar? If yes, doing it later means a minor bump, and `minor` lives in genesis (`fold.js:265`), so a later bump re-ids every world: the migration this freeze is trying to be the last of.

## 0. What the code does today (verified)

- **Ids.** `u-` + 20 base32 chars = 100 bits, minted at random per server (`directory.ts:32-33`), **server-wide, one per account, the same in every world on that server** (`directory.ts:11-13`: per-world ids "were tried and withdrawn", R 10-06). The id→person map (`name`, `subs`, `kind`) is a 0600 file, never logged (`directory.ts:5-9`). A `sub` is `human:…` (issuer-signed session), `agent:token:<name>`, `aid1:<iss>:<sub>` or `local:<name>` (`directory.ts:14-17`, `ACCOUNT_SHAPE` :38). A guest is a fresh in-memory id per connection (:19).
- **Nothing cryptographic binds a person to an id.** The only key-shaped thing a person can hold is the founding `ownerKey` (tier 0 of genesis, §13), and translated worlds have an empty tier 0 (§14). The chain's `sig` is the host's sequencer key (`custody.ts:74`); the operator key countersigns receipts and approvals (:60-64). Both live in the host's `.custody.json`.
- **A cross-host credential already exists for agents**: `aid1.<payload>.<sig>`, an Ed25519 bearer token from an issuer (archipelago-home) verified offline against a pinned issuer key (`aid1.ts:5-7`, `auth.ts:19-25`). Its `sub` is a durable principal id like `agent:<name>@<domain>` (`aid1.ts:21`). It is issuer-rooted, not self-sovereign: the issuer's key, not the person's, is what a door trusts. The directory then mints a server-local `u-` for it like any account.
- **Stand-ins.** The translator mints an unclaimed name's id as `HMAC(salt, "name:<name>")` → `u-`+20, where `salt = HMAC(custody secret, sha256(old log))` (`import-v1/world.ts:102,151-153`): stable across dry-run and apply, unlinkable across hosts. Claiming is `directory.bind(id, sub)` (`directory.ts:112-118`) — an operator act outside the log that lets an account wear the id; a second id for the same account is refused with "alias merge, coming with portable identity" (:116). Roles stay on the stand-in id, untouched.
- **The envelope** is kernel (`fold.js:21`); an unknown field makes the entry malformed, status `ok` (:184, design doc §0). The skeleton drops only `head` and `sig` (`chain.py:80`); request/say/physics bodies hash as `{commitment}` (:81-82). `actor` is in every skeleton.
- **`checkGenesis` enforces `ed25519:` on every `owners` key and on `sequencer`** (`fold.js:271,273`, `keyOk` :257); `gov.py` likewise (`:111,120`) and verifies governance `sigs: [{key, v}]` over `eidoverse-gov:<world id>:<seq>:<JCS(body minus sigs)>` by tier (`:24-34,129-132`).
- **`actor` is stamped from the authenticated connection** (§6; the request path never reads it from the payload). `messages.ts:40` and `presencewire.js:99` check the `u-` shape on the wire.
- **R's own framing** (WISHLIST 🪪 and 🌱, 10-18/10-21/10-27): "probably a signed identity you carry (keys, like the archipelago id), not accounts a server holds for you"; "an id minted only by your own computer"; open questions were key loss, several devices, linking to an account later, rate-limiting free keys, what `guest` means after keys.

## 2. Answers for this protocol

### 2.1 What an identity should be

**A self-certifying identifier: the truncated hash of a signed identity-genesis operation** (did:plc's construction, Keybase's chain), written in the log's alphabet as `u-` + 24 lowercase base32 characters (120 bits; did:plc's own length). Its **document** — the thing the id resolves to — is an append-only, self-signed operation log holding:

- `signing` keys: one per device (a browser's IndexedDB key, a passkey, an agent's process key), each able to sign requests;
- `rotation` keys, **ordered**: a higher key can nullify a lower key's operations within a recovery window (72 h is the did:plc precedent; make it a setting, R's "rails are settings"), and the person's own recovery key sits above their home node's. Losing a device key is a rotation op signed by a surviving key; losing *every* key is where the home node's lower-priority rotation key, or a paper recovery key, comes in. **The id never changes**, so no world log is touched by any of this: that is the whole point of hashing the genesis rather than using a key;
- `alsoKnownAs`: handles (`name@host`, reverse-verified like NIP-05/AT handles) and **claimed local ids** (today's random `u-`+20 ids and stand-ins), each with the minting host's countersignature (the two-sided `Move` attestation);
- `services`: the home node that serves this op log (archipelago-home is the obvious first one — it already issues Ed25519 principal credentials, `aid1.ts`), and any mirrors.

**Why not the alternatives, in one line each.** A bare key (Nostr, did:key, SSB, wallets): rotation impossible, loss total — fails the owner's rule outright. `did:web`/`name@host`/MXID/AP-URL: bound to a server or domain in the record; every one of those ecosystems is still trying to undo it. A server-scoped id *with a binding* (today, plus a signature): keeps hosts in the loop for every resolution and makes "the same person on two hosts" a matching problem forever. Issuer-rooted tokens alone (`aid1`): the issuer's key is the root, so the issuer can mint "you"; fine as a *home-node service* under a self-certifying id, wrong as the id. Agents (AIs) go through exactly the same path: an agent's process holds a signing key under an identity whose rotation key the operator (or the agent's own home) holds — the `declares` status (§6a rule 3) stays presence, never in the document.

Where the op log lives is a product question, not a protocol one, and it does not need deciding now; the format can copy did:plc's op schema (CBOR-signed, `prev` CID, `rotationKeys`, `verificationMethods`, `alsoKnownAs`, `services`) or Keybase's JSON links. **Guess:** did:plc's schema is the one with living tooling (`goat`, the spec's test vectors) and is the better 10-year bet.

### 2.2 What that requires of the log now

- **`actor`.** Stays the opaque `u-` id (F1), and **by default it is a world-visible alias whose binding lives outside the log**: the host mints or accepts a per-host or per-world local id bound to the portable id in the person's document (the MSC4014 shape; §2.5). A person holding a portable identity MAY elect one spelling across worlds, including the portable id itself (24 chars), as an explicit choice; the host never writes the global self-certifying id as the actor automatically, because that would make portability irreversible global correlation by default (review 2, P1). "The same person between worlds" (the 10-06 ask) is met by the binding, which the person controls, not by the actor bytes. Old entries keep their old ids; the alias is resolved outside the log. Nothing the fold or the chain does changes.
- **Per-actor signatures: yes, later, in the body.** A request's signature (over `{world, verb, args, nonce, exp}`, by a signing key in the actor's document) belongs in the `request` body, not the envelope (F2). It is purgeable with the body: a redacted request keeps its `commitment`, which still binds the bytes the signature was over, so verifiability is "the commitment stands; the signature is gone with the words it signed" — the same deal every redaction already makes. The authority still stamps `actor` from the connection (§6) and *checks* that the body's signature verifies under that actor's document; a mismatch is a refusal. A `say` can carry the same. `change` entries are the authority's own and stay unsigned by the actor (the request that caused them is the signed thing; `cause` points at it).
- **Binding / claim: a request verb, not a kind or a governance verb** (F5). Shape (names not frozen): `request {verb: "claim", args: {of: <stand-in id>, proof: {…}}}` where the proof is signed by the claimant's identity key *and* countersigned by the host that minted the stand-in (it is the only party who can vouch that `name:<old name>` was that person — the HMAC salt is the host's, `import-v1/world.ts:151`); the authority admits it and writes `change`s by `system` (`cause` = the request): `set roles:<claimant>` with the stand-in's value, `delete roles:<stand-in>`, and the same for `imported-roles:`/`imported-bans:` keys. Old `actor` values stay the stand-in id for ever; the claim is the public bridge. A fork made *before* the claim copies `roles:<stand-in>`; the same proof claims it there (it names the stand-in and the minting host, not a world). A fork made *after* copies the moved roles and needs nothing.
- **Genesis `owners` may name an identity** (F4), so a founder's lost device never loses the world and a translated world's empty tier 0 can later be filled with an *identity* (§13's "one attested fill"), not a key that will itself one day be lost.
- **Governance `sigs`** stay `{key, v}`; the verifier resolves `key` to a tier element either directly (a key) or through the identity's document **at the version bound by the entry** (F6): the identity id, the document / op-log version or CID, the key valid at `ts`, and the proof history, all retained so the check runs offline and survives the home node rotating or vanishing. The gov message keeps binding the world id (D11).
- **The receipt** (D8) can grow `ownerAttested: {id, key, sig}` later: it is outside the log. For a founder-keyed world `ownerAttested` is mandatory before any output (design doc D12).

### 2.3 Now vs later, strictly

**Now** (bytes, genesis, kernel, or a guard that prevents a future collision): F1–F7 in the table at the top. Their hash effect today is *nil*: none of them changes a byte of any existing or migrated world; F3/F4 widen grammars inside the minor-1 kernel pin that this freeze is already re-pinning.

**Later, additive, no migration** (bodies the skeleton hashes as `{commitment}`; code outside the log; new request verbs):
- the `request`/`say` body signature field and its verification;
- the claim verb and its system changes;
- UCAN-shaped delegation in the request body (`sub` + proof chain), the thing D4 reserved in prose;
- the identity document format, op log, home-node protocol, mirrors, handle verification;
- the directory becoming a *cache* of documents + a local alias table;
- pairwise/local ids as a per-person choice (§5) — needs nothing because of F1;
- friends, DMs, profile, the "client home" surface.

**Would force a migration if done later, so either do now or never**: a new entry kind (`claim`, `identity`), a new envelope field (`for`, `sender_key`, `proof`), a change to what `actor` may contain beyond F3's grammar, a non-key founder in `owners`. F2, F4 and F5 close each of these.

### 2.4 Interactions with the design doc

- **Redaction** (D3, §12). An actor id is skeleton; actor history is never redacted (F7). Retiring or revoking a local binding tombstones the **directory relation** (and a person may tombstone their own identity document, as did:plc's `tombstone` does, so the id resolves to nothing): neither act touches the person's historical authored entries. Their request/say bodies may be redacted as today; their signatures go with the bodies and the commitments stay. Because the id is a hash of a genesis op, not a name or a key, an orphaned `actor` reveals nothing by itself — but see §2.5 on linkage.
- **Governance signatures binding world ids** (D11). Unchanged; F6 adds how a signer's key is found. D11's "genesis-changing migration impossible after the first governance entry" is one more reason F4 must be now: after this migration, no world can be re-founded with an identity owner.
- **The receipt** (D8, D12). `ownerAttested` was defined as a tier-0 *key* signature; with F4 it may be an identity's signing key resolved through its document (at the bound version, F6). For a founder-keyed world the tier-0 signature is required **before** migration produces any output; a countersignature supplied later ratifies a receipt only if nothing migrated has been served or mutated (Q4, answered). Translated worlds have an empty tier 0, so they are custodial-default and the operator may migrate them; a later owner claim does not re-run the migration.
- **Forks copying role grants** (D9, §6). Handled under 2.2's claim: the proof names the stand-in + minting host, so it works in any copy. Forks are not re-id'd by claims (claims are not genesis).
- **`actor` never read from a request's payload** (§6). Still true and now *checkable*: the body's signature must verify under the stamped actor's document. Delegation later keeps it: `actor` is the invoker (UCAN `iss`); whom they act for is body (`sub`).
- **D4** (drop `for`/`grant`) is confirmed by every surveyed system that does delegation well (UCAN, NIP-26's tag): it lives in the signed payload.

### 2.5 Risks

- **Correlation.** One id everywhere = one person's whole life linkable across every world and host (Nostr, AT, Keybase all accept this; AT mitigates nothing beyond "handles are pseudonyms"). DID-land's answer is **pairwise DIDs** (`did:peer`, Aries): a different id per relationship, all controlled by one wallet, the linkage known only to the owner. Matrix's answer is MSC4014's per-room pseudonymous key with a removable alias. **This protocol's answer costs nothing because of F1**: `actor` is a local alias by construction, so a person may hold one portable identity and present a distinct `u-` per host or per world, with the binding in their *own* document (private) or a host's directory (shared) rather than in any log. The default is the local alias; one spelling across worlds, or the portable id itself as the actor, is the resident's explicit choice (F1, review 2). Caveat: a pairwise id gets no cross-world standing (bans, reputation) by design — that is the trade.
- **Free keys = sanction evasion** (R's 10-21 question). A self-certifying id is free to mint; standing must be *earned* per host (account age, an issuer vouch in `services`, a paid/attested handle). The §7a guest rule already says a guest "cannot found a world"; "guest" becomes "an id no host has standing for".
- **Recovery window = a 72 h rewrite window.** Someone holding a higher rotation key can nullify your ops for 72 h; that is the feature and the attack (Buchanan's "adversarial PDS migration"). Keep the person's own key above the home node's, and make the window a setting.
- **100-bit ids.** Today's 20-char random ids are fine as random (collision 2^-50 at 2^25 ids). A *hash-of-genesis* id at 100 bits is second-preimage safe but birthday-weak against an attacker colliding two of their *own* genesis ops (2^50 work): low harm (both halves are theirs) but it is why did:plc chose 120. Hence F3's 24 for portable ids.
- **Home node down.** Resolution fails for new hosts; hosts that have met the person keep their cached document (mirrors). Same failure mode as a PDS outage; the id survives it.
- **Scope creep.** Everything after F1–F7 is a product; the freeze needs none of it. The risk is reserving *more* than this list (a field, a kind) "to be safe" — the reviewer's rule is right.
